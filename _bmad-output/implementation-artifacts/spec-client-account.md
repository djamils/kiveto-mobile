## Intent

**Problem:** The Compte tab (screen 6) is still the phase-5 placeholder with a lone « Se déconnecter »: the owner cannot see or edit the profile, change or verify the e-mail, see the clinics and switch, set the consents of the active clinic per message kind and channel, export the data, or ask for the account's deletion — all of which the Portal API offers (`/me`, `/me/email-change/*`, `/clinics/{c}/consents*`, `/me/data-export*`, `/me/deletion-request*`).

**Approach:** Build screen 6 in `client` the way mockup 06 draws it (profile card, « Mes cliniques », « Consentements », « Mes données », « Se déconnecter »), with the undrawn states as sheets in the mockup's language (profile form, consent history, exports); the e-mail change and the deletion are `identity_access` sheets (SMS code → action → for the e-mail a second code), called by the page through `identity_access.dart`. The server decides every rule; the app shows its answers.

## Boundaries & Constraints

**Always:**
- D15 layers (CLAUDE.md §3, `test/architecture/`): domain and application pure Dart; DTOs stay in infrastructure; presentation never imports infrastructure, Dio, the client, `core/network`, `core/security`. Repositories **throw** `ApiFailure` (through `apiFailureOf`). `client` presentation may import `features/identity_access/identity_access.dart` (identity_access imports no feature: no cycle); identity_access must NOT import `client`.
- Account-scoped providers watch `sessionStatusProvider` and are read through `AsyncData` patterns / `AsyncValueView`, never `.value`. The consents provider follows the active clinic id only: `ref.watch(sessionStatusProvider); final clinicId = await ref.watch(activeClinicProvider.selectAsync((c) => c?.clinicId));`.
- After a successful `PATCH /me`, a clinic switch, a consent change and a verified e-mail: `ref.invalidate(meProvider)` (header, initials seam, active clinic follow).
- Files through `portalFileDownloaderProvider` (`'/api/portal/v1/me/data-exports/$id/file'`), never the generated `getDataExportFile` / `FilesApi.downloadDataExport`. The ZIP goes to the share sheet behind a seam provider (as `calendarSharerProvider`).
- Every user-facing string in `lib/l10n/app_fr.arb` (then `fvm flutter gen-l10n`), French; a literal no-break space U+00A0 before « ? ; : ! »; no elision before a name; no channel promise for clinic messages (OTP texts may name the phone: the API sends those codes by SMS to the account's phone). Copy in Design Notes.
- Kit widgets by C-id (notes-app-shell §7); material from `package:material_ui/material_ui.dart` only; custom sizes via `kivetoTextStyle`.
- 100% line coverage of every new domain / application / infrastructure file (tests on the captured fixtures listed in the Code Map). Enums keep an `unknown` case for unknown wire values; enum mapping by name (`asNameMap()`), never the generated `toJson` of `unknown`.
- Destructive actions need an explicit tap: the deletion is never sent on the OTP's 6th digit.

**Never:**
- No client-side business rule: no blocking of the last channel of `billing` / `clinical_documents` (send it, show the 422), no e-mail format check (only « not empty »), no OTP/export quota logic, no name-length check.
- No new dependency (share_plus 13.3.1 is already pinned). No edit of `contracts/`, `packages/kiveto_portal_api/`, `CLAUDE.md`, `.claude/settings.json`. No backend change.
- No global « Recevoir les messages par SMS / Email » control (the API stores channels per kind, mockup-vs-contract.md). No country field (keep the address's `country`, `FR` when none). No clearing of the address (the API cannot).
- Screen 10 (`/clinics`) stays the placeholder (slice 7).
